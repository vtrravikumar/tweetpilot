# M2.6 Deployment Preparation

TweetPilot's first production deployment is intentionally small:

```text
Cloudflare Worker
  /health
  /v1/tweet/generate
  OpenAI Responses API
```

No database, KV, R2, queues, scheduled jobs, Durable Objects, Hyperdrive, or custom domain are required for the first deployment.

## Current Worker Configuration

The Worker configuration lives in `backend/wrangler.jsonc`.

- Worker name: `tweetpilot-api`
- Entry point: `src/index.ts`
- Compatibility date: `2026-08-22`
- Observability: enabled
- Cloudflare bindings: none
- Routes/custom domain: none
- Production URL target: the standard `tweetpilot-api.<account>.workers.dev` URL assigned by Cloudflare

## Runtime Configuration

Local development uses `backend/.dev.vars`, which is ignored by Git. Production values must be set through Cloudflare Worker secrets or variables, not committed config files.

Required production secret:

```text
OPENAI_API_KEY=<set via Wrangler secret or Cloudflare dashboard>
```

Optional production variables:

```text
TWEETPILOT_GENERATOR=openai
OPENAI_MODEL=gpt-5.6-luna
OPENAI_REASONING_EFFORT=none
CORS_ALLOWED_ORIGINS=chrome-extension://<extension-id>
VTRRK_LINKS={"photography":"https://<verified-url>"}
```

Notes:

- `TWEETPILOT_GENERATOR` can be omitted in production because OpenAI is the default when `OPENAI_API_KEY` is present.
- `OPENAI_MODEL` can be omitted to use the code default, currently `gpt-5.6-luna`.
- `OPENAI_REASONING_EFFORT` can be omitted to use the code default, currently `none`.
- `VTRRK_LINKS` can be omitted until verified VTRRK URLs are ready. Non-HTTPS URLs are ignored.
- `CORS_ALLOWED_ORIGINS` should be exact origins only. Do not use `*`.

## CORS Decision

The Chrome extension/browser context needs CORS, but the final production extension ID may not be known during deployment preparation. The Worker therefore uses an exact-origin allow list controlled by `CORS_ALLOWED_ORIGINS`.

When unset, no CORS headers are emitted. When set, only matching origins receive `Access-Control-Allow-Origin`. Valid preflight requests are accepted only for configured origins, existing route methods, and the `content-type` request header.

The initial deployment should allow only the actual TweetPilot Chrome extension origin. Do not add `https://x.com` speculatively. If M1/content-script integration later demonstrates a genuine requirement for `https://x.com`, add it deliberately at that time.

## Usage Protection Decision

The existing `UsageGuard` abstraction remains in place with the allow-all implementation. A reliable shared limit would require Cloudflare-managed rate limiting or shared state such as KV/D1/Durable Objects, which this first deployment intentionally avoids.

For the first controlled deployment, cost containment is handled by:

- not publishing broad CORS access;
- requiring a server-side OpenAI key;
- capped prompt fields;
- capped output tokens;
- a 15 second upstream timeout;
- one corrective retry maximum;
- `store: false` on OpenAI requests.

If the endpoint becomes public or shared, add a Cloudflare-side rate limit or a persistence-backed guard before broad rollout.

## Security Review

The current implementation keeps the API key server-side and never returns it in API responses. OpenAI error payloads are not forwarded to clients, and logs include only the TweetPilot error category and upstream status.

Request validation accepts only a JSON object with a non-empty `topic`, optional string `location` and `style`, and optional positive safe-integer `maxLength`. Unknown fields are ignored for forward compatibility. Oversized prompt fields are clipped before OpenAI requests to limit token cost.

Generated output is rejected if it is empty, malformed, over `maxLength`, or contains a URL other than the selected configured VTRRK link. Configured VTRRK links must be HTTPS.

The main remaining risk is that `/v1/tweet/generate` has no durable rate limit. Keep the initial deployment controlled and CORS-restricted.

CORS is a browser access-control mechanism; it does not prevent direct non-browser requests to the Worker URL. Treat the initial deployment as controlled/smoke-test use, do not broadly distribute the endpoint while `UsageGuard` remains allow-all, and add durable rate limiting or abuse protection before broad public rollout.

## Health Check

`GET /health` returns:

```json
{ "status": "ok" }
```

It does not require `OPENAI_API_KEY`, does not call OpenAI, and does not expose internal configuration.

## Local Development

Use:

```sh
cd backend
npm run dev
```

Local secrets stay in `backend/.dev.vars`.

## Pre-Deployment Validation

Run these before creating production secrets or deploying:

```sh
cd backend
npm run typecheck
npm test
npx wrangler deploy --dry-run
git status --short --branch
git diff --check
```

Stop here during M2.6 review.

## First Deployment Runbook

After review, use this sequence for the first real deployment:

1. Run tests.
2. Run typecheck.
3. Run Wrangler dry-run.
4. Confirm the Git working tree is the intended reviewed state.
5. Set the production secret:

```sh
cd backend
npx wrangler secret put OPENAI_API_KEY
```

6. Set any production variables needed by the first extension build. For example, configure `CORS_ALLOWED_ORIGINS` through the Cloudflare dashboard or Wrangler-supported variable management.
7. Deploy:

```sh
cd backend
npx wrangler deploy
```

8. Check health:

```sh
curl https://tweetpilot-api.<account>.workers.dev/health
```

9. Run one real generation smoke test:

```sh
curl -sS https://tweetpilot-api.<account>.workers.dev/v1/tweet/generate \
  -H 'content-type: application/json' \
  --data '{"topic":"Photography","maxLength":140}'
```

10. Inspect Worker logs/errors and confirm there are no repeated failures.
11. Confirm cost behavior: model is `gpt-5.6-luna`, reasoning effort is `none`, `store` is `false`, output tokens are capped, and there is at most one corrective retry.

## Rollback

For a bad deployment, roll back to the previous Worker version from the Cloudflare dashboard or by redeploying the last known-good Git revision:

```sh
git switch --detach <last-known-good-commit>
cd backend
npx wrangler deploy
cd ..
git switch main
```

Do not rewrite `main`, reset `main`, force-push, or leave the normal working tree checked out at the rollback revision. Do not delete secrets during a normal rollback unless the incident is specifically secret-related.
